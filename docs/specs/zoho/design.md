# Zoho provider family — discovery and proposed implementation

Date: 2026-11-13. Source revision inspected: a02c4219. This specification covers adding CRM, Desk, Voice and other services available with a Zoho One subscription. No implementation or authorization has been completed. A subscription label alone does not establish per-product entitlement.

## Outcome and coverage

Make Zoho apps separately searchable and connectable in Open Connector with explicit actions/scopes and independent named accounts. CRM, Desk, Voice are the first implementation batch. Each product can pass acceptance and ship independently; a missing Voice subscription or unsupported region never blocks CRM or Desk. Keep the blocked product visibly pending rather than claiming the batch complete. Remaining Zoho One apps stay in scope through [coverage.json](coverage.json) and the readable [coverage table](coverage.md). Its 50 distinct plan sections include one app/device-management feature section; they are not 50 verified API providers. Regional Payroll variants are collapsed. Voice is an additional explicitly requested product. A directory link establishes documentation availability only, not verified execution. Missing directory entries remain discovery work, never silently dropped or published as working integrations.

The inventory is public-plan based. Account enabled apps, exact plan, region, organization IDs, API roles/limits, and active Voice subscription remain unverified. The general Zoho global-navigation menu must never determine bundle inclusion. The official Voice FAQ says Voice has a separate subscription; integration with Zoho One does not establish licensing. Do not buy or enable paid services automatically.

## Existing boundaries and decisions

ProviderDefinition in src/core/types.ts supports comma-separated scopes, authorization parameters and client configuration fields. Provider-local OAuth overrides in src/oauth/oauth-token.ts support authorization URL construction, code exchange, refresh and stored providerSecret. src/providers/salesforce/oauth.ts demonstrates region/instance handling. src/oauth/oauth-credential-refresh-service.ts preserves an old refresh token when rotation omits one. src/server/api/console-oauth-routes.ts owns /oauth/callback. src/core/provider-definition.ts owns action IDs/classification/scopes. src/server/cloudflare-embedded.ts owns asset-backed catalog startup; executor imports remain lazy.

Use separate proposed service IDs zoho_crm, zoho_desk, zoho_voice. Put definition.ts, actions.ts, executors.ts and oauth.ts under each service directory. Reuse a small shared Zoho helper for verified regional endpoint mapping, token normalization and request authentication; exact helper location must follow registry generator discovery rules (inspect scripts/generate-provider-registry.ts before creation). Use shared provider-runtime HTTP helpers rather than cloning timeout/error logic. No database migration is needed. Two narrowly scoped shared changes are required: freeze Zoho client configuration when authorization starts, and sanitize raw OAuth callback error values in logs. Existing non-Zoho consent behavior otherwise remains unchanged.

Each app has its own consent and encrypted connection. One server-based OAuth application may be reused if supported by the registered client/region, but current OAuth-client configuration is per service: configure the same client through each service's existing OAuth Apps form. Do not promise one click, a universal Zoho token, auto-provisioned apps, or automatic cross-service revocation. A later shared client-settings UI is a separate feature. Do not use instance-level ORG OAuth in the first release.

Register `<OPEN_CONNECTOR_ORIGIN>/oauth/callback` on a server-based client. Request offline refresh and comma-separated product scopes. Start with read scopes for the initial validation release (a proposed release boundary, not a stated user preference). Each selected app must be consented separately. Client secrets enter through existing protected OAuth settings or an approved secret manager, never chat or logs. Human login/consent is a necessary external step; no live account access exists yet.

For the three Zoho service IDs, prepareAuthorization must set pending.clientConfig to the normalized client configuration even when starting with the saved default. Require the existing encrypted-storage capability guard for every Zoho snapshot path, including the default-config startAuthorization path; fail before storing client secrets if the codec is plaintext or unavailable. With that guard, the existing state store encrypts it. It must also populate oauthClientConfig in the resulting encrypted credential metadata, as the current explicit-config path already does. The callback and refresh both use that frozen config. Test a Desk A consent started before settings change to B; A must retain A, and a later B consent must retain B. Repeat for region/client changes and both existing authorization entry points. Region is explicit client configuration and is preserved with the connection. Validate callback location/accounts-server and token api_domain against exact, documented origin mappings; reject userinfo, ports other than 443, non-HTTPS, unapproved hosts, extra path/query and region mismatch. Never fetch an arbitrary callback URL or use suffix matching to approve endpoints. CRM uses the validated zohoapis host; Desk and Voice use product-specific regional host mappings. Only include regions whose per-product host mapping is verified from official docs; fail unsupported regions clearly. Never assume api_domain is the Desk/Voice API base or silently fall back to US. No host/organization overrides in action input.

## First release contracts and unresolved endpoint details

CRM: list_modules, list_fields, list_records, get_record and search_records. Use API v8. list_records requires fields (1–50 API names), moduleApiName, perPage up to 200, mutually exclusive page/pageToken; get_record requires moduleApiName and string recordId. Preserve all long Zoho IDs as strings. Returned pagination includes upstream continuation values without auto-draining the account. Start with Leads, Contacts, Accounts, Deals and Tasks with explicit read scopes plus metadata scopes; custom module execution waits for its verified scope mapping. Reject unsupported module/scope combinations before HTTP. Inspect field/search endpoint docs before schema implementation. No raw arbitrary URL or generic HTTP proxy exposed.

Desk: list_organizations (bootstrap), list_departments, list_tickets, get_ticket, list_contacts and get_contact. Store the explicitly selected Desk orgId on the named connection and send the required header for organization-specific endpoints. Do not pick the first org if several exist. Use an optional deskOrgId field in the existing per-service OAuth clientConfigFields (config.extra), then freeze that selection into providerSecret at exchange. If absent, allow only list_organizations; organization-specific actions fail locally with an instruction to select an org in OAuth settings and reconnect. list_organizations calls GET /api/v1/organizations without orgId; the official docs list Desk.organization.READ and Desk.basic.READ and show no orgId header in its example. Verify whether those scopes are alternatives before freezing action metadata. To switch organizations or create another named connection, update the field and authorize that connection; existing connections retain their frozen org. No new form type or post-consent picker is needed. IDs remain strings, pagination follows Desk docs.

Voice: list_call_logs and get_call_log with ZohoVoice.call.READ; read-only access to /rest/json/zv/logs and /rest/json/zv/logs/{logId} on the verified regional Voice host. Other requested useful actions (users, contacts, queues, SMS history, existing transcription retrieval) are later candidates after endpoint and scope verification. Read operations do not generate transcriptions, send SMS, dial, buy numbers or schedule recording exports. Recording media is not fetched in the first release; do not expose signed recording URLs unnecessarily. Check the per-call docs for status/envelope, parameters, region support and mandatory tenant selector before freezing schemas.

The prior paragraphs define the first release direction, but the marked scope and endpoint/region details are readiness gates for implementation, not blanks an implementer may guess. Public metadata alone does not justify a production launch.

## Failures, token lifecycle, isolation

Reuse existing OAuth state verification and encrypted storage. Code exchange is single use. Refresh via the connection's validated account host and original OAuth client configuration; preserve a prior refresh token if absent in response. Preserve product/tenant/region state when refreshing. Explicit invalid_grant becomes reconnect-required; transient provider failures must not erase a working connection. src/connection-service.ts coalesces refreshes per connection/token/authorization within one service instance and fences stored updates by revision; reuse it and add Zoho coverage. This is not a claim of cross-isolate single-flight. Zoho refresh tokens must not be required to rotate on each refresh. Do not invent an independent token store. The default local OAuth config can change after consent; use frozen providerSecret for region/tenant, require the same oauthClientId on refresh by comparing the frozen credential and frozen config, and fail with reconnect-required if those frozen identities disagree instead of sending an old token to another client/region. Editing the current service default from A to B must not invalidate existing A connections or redirect their refreshes. This guard compares only their stored pair, not current global defaults. Do not claim the framework already snapshots all default client credentials.

Honor product-specific rate errors and Retry-After through existing error contracts. Do not retry writes or replay OAuth code exchanges after uncertain results. Future create/update/delete/send/dial actions must be individually classified and scoped. Validation in this release makes no external writes. Disconnect deletes only the selected local account; remote token revocation is not advertised until Zoho behavior and region-aware support are verified. Never log tokens, raw credential responses, account content or callback query values. In console-oauth-routes.ts remove raw providerError/providerErrorDescription from callback logger contexts; log only a bounded internal category such as denied/provider_error and presence booleans. Add a logger-capture regression test with sentinel callback strings, including non-Zoho paths. Existing callback responses need not change in this limited logging fix.

## Alternatives and rollout

A single universal provider with a generic HTTP action would hide product/tenant permissions and make action discovery worse; reject it. Direct official Zoho APIs preserve local action and connection policies. Zoho-hosted MCP/Flow is an optional later route; it does not automatically add providers to this catalog.

1. Resolve account region, Voice entitlement and per-product endpoint/tenant contracts; record official links and response fixtures. This can proceed without passwords.
2. Implement shared OAuth/transport plus separate CRM, Desk, Voice providers and focused mock-HTTP tests in an isolated worktree. Do not edit generated registries by hand.
3. Generate registry/catalog, validate action examples and run npm run fix-check plus relevant OAuth/provider/runtime/catalog tests.
4. Deploy isolated staging with minification retained; compare previous 1650 providers for regressions and add only implemented Zoho entries. Verify startup, schema loading, MCP discovery, invalid input without upstream calls, and policy denial before upstream calls.
5. Configure OAuth client securely and obtain per-app consent. Verify read-only access, correct tenant selection, refresh and reconnect with user account; no account mutation or purchase.
6. Promote a tested release using private production backup and existing keep-vars/binding/data checks. Existing connections, client configurations, runtime tokens and policies must remain intact; compare against a fresh pre-deployment baseline while allowing legitimate last-used timestamp changes. Never label mocked-only account tests as live success.
7. Work through the entire coverage.json backlog in batches. Proposed next priorities: Mail, Calendar, WorkDrive, Books, Inventory, Projects and Cliq, then the remaining API-documented apps; research missing-directory entries alongside those batches. This ordering is an implementation recommendation, not a user preference. An app is complete only when its documented supported-action subset, credentials, actual entitlement and read-only live tests are all recorded; unsupported/non-API apps get an evidence-backed limitation and remain distinct from connected apps. For each, distinguish documented API, implemented actions, credential configured, account entitled, live verified. Broader permission and outbound-action rollout is a separate reviewable step; this design does not declare all Zoho apps implemented.
